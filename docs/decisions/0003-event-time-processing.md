# 0003: Process readings by event time, not arrival time

- Status: proposed
- Date: 2026-11-22
- Deciders: Abdullah, Hanan

## Context

Wearables lose connection, buffer readings and send them later, sometimes out of order and sometimes more than once. If detection used arrival time, a buffered burst could look like a sudden spike, a gap could hide a real event, and a heart rate episode could be split or merged wrongly. Alerts also need to say when something happened, not when the server noticed.

## Decision

1. **Every reading carries `event_time`**, the time the device took the measurement, in UTC (RFC 3339 with offset). Ingestion adds `received_at`, the server time the message arrived.
2. **Detection windows use `event_time`.** For example, "heart rate above 120 for 60 seconds" means 60 seconds of `event_time`, regardless of how the readings arrived.
3. **Duplicates are dropped** using the pair (`device_id`, `message_id`). `message_id` is a UUID generated by the device per message and reused on retry.
4. **Allowed lateness.** Each detection keeps a watermark per device. Readings that arrive within the allowed lateness (starting value: 5 minutes, configurable) are processed normally, even out of order.
5. **Late detections are flagged.** Readings later than the allowed lateness are still stored. If they cause a detection, the alert is marked `late: true` so caregivers and metrics can tell it apart.
6. **Future timestamps are rejected.** Readings with `event_time` more than 2 minutes after `received_at` are treated as a device clock error, rejected and counted in a metric.

The numbers in 4 and 6 are starting values and will be tuned after the first simulator runs.

## Consequences

- The simulator must be able to produce delayed, out-of-order and duplicate messages so this behaviour can be tested.
- Detection code needs per-device state (window plus watermark), which affects how the ingestion and engine modules scale later.
- Metrics needed: lateness distribution (`received_at - event_time`), duplicates dropped, readings rejected for clock error, late alerts.
- Device clocks must be reasonably accurate. Clock drift on real hardware is out of scope for now.

## Alternatives considered

- **Arrival time:** simplest, but gives wrong windows and misleading alert times under normal network behaviour.
- **Drop all late readings:** loses data and could miss real events. Flagging keeps the data and makes lateness visible.
